## Authentication and isolation

`market-functions/src/index.ts` routes `/api/owner/usage` before market admission. Firebase Admin verifies the signature, issuer, audience, expiry and revocation/disabled-user state against **bazaarsignal**. The handler additionally requires token email **drewstake3@gmail.com**, `email_verified: true`, and `firebase.sign_in_provider: google.com`. Browser-supplied email and UID parameters are ignored. Every data request is verified, including cached responses. Unauthenticated requests return 401, verified other identities return 403, and no diagnostic cloud errors or data accompany failures. CORS preflight contains no data. Credentials come from the existing Cloud Run service identity and never enter browser code, URLs, logs or the response.

Responses have `Cache-Control: private, no-store`; browser state clears on sign-out or identity change. No usage data is stored in localStorage, IndexedDB or public Hosting files. The private Firestore cache is `marketCache/usage-dashboard` in the collector project, whose existing rules deny all client reads/writes. IAM-controlled server reads are separate from Firebase client rules.

The existing `market-reader` runtime uses custom read permissions: `monitoring.timeSeries.list` in both projects, `firebaseauth.users.get` for main-project revocation checking, and `cloudscheduler.jobs.list` in the collector project. The coverage improvement adds `cloudbuild.builds.list` in the collector project and `datastore.entities.get` in the main project. The latter is project-scoped IAM read permission (Firestore IAM does not restrict it to a document); application code reads only the fixed `backend/worker` control document and returns selected aggregate quota/budget fields. It never returns that document, its user cursor, alert ledgers or build configuration. No list/write permission, credential key, billing change, API enablement or paid service was added.

## Measurements and quota footprint

`collector/usage-dashboard.ts` reads the existing `LiveAllowanceState` from `collector/allowance-live.ts`, its observed collection status and Google system metrics. It does not admit market work, invoke Hypixel, construct a collector, change the ledger, run cleanup, reset counters, renew the deadline or resume/stop a service. The current operating period and November 1, 2026, 07:00 UTC deadline are retained.

The shared durable cache permits at most one measurement attempt per 30 minutes, including failures, eviction and restarts. CAS prevents overlapping instances from measuring twice. Requests coalesce in-process, with a short memory cache; a cached response still requires token verification. One request per minute per running process is admitted for the owner, and the browser disables refresh for a minute. Responses support gzip. There is no automatic dashboard polling, new Scheduler job or custom Monitoring metric. Platform/unauthorized requests still consume some Cloud Run resources outside collector reservations.

Google DELTA counters use full, complete clock hours with an explicitly aligned end time and `view=FULL`. This avoids sliding first-bucket inclusion before the daily/monthly boundary. Counters are partial reported operational usage, not settled bills; missing series are **Not yet reported**, and errors, incomplete pagination or invalid values are **Unavailable**. A reported numerical zero is retained only when Google actually reports it. Gauges use the latest raw point per series, retaining its original timestamp; historical capacity samples are never summed over time. Responses and pages are bounded; oversized/incomplete results fail visibly rather than becoming a total.

Measured resources include Run requests, CPU (vCPU-seconds), memory (the descriptor already reports **GiB-seconds**), sent bytes, selected Storage Class A/B methods, capacity/transfer, Scheduler inventory, repository size, Hosting, auth activity, Firestore operations/storage and log ingestion. Account-shared allowances are clearly identified; remaining allowance is an upper bound when other projects, geography or operation classes are unmeasured. Firestore daily counters use Pacific midnight including DST. Monthly comparisons use the Pacific calendar. Spark Hosting's 10 GiB monthly transfer enforcement was checked against its `monthly_sent_limit` metric; the published Blaze daily pricing is distinct. Capacity does not reset to zero each month.

Projections extend the reported usage rate across the same period, including idle hours. They are estimates and particularly uncertain early in a period. Capacity has no rate projection. The app's actual reservation and budget values come directly from the existing ledger, including its own daily date; they are not subtracted from measured consumption or called charges. Google free pricing benefits are not a hard spending cap.

The dashboard now connects two previously unavailable measurements with three additional reads per eligible cache refresh:

- **Email quota:** one read of the worker's existing saved `MailApp.getRemainingDailyQuota()` reading. Allowance consumed is 100 minus Google's remaining recipients, shared across the consumer sender account. Missing, invalid, future or older-than-30-minute readings stay unknown. This is quota consumption, not a count inferred from alert records. Google's exact rolling reset time is unavailable, so no false midnight reset or daily projection is shown.
- **Cloud Build:** two bounded history requests, one each for the existing `us-central1` deployment region and legacy `global` region, with at most 100 records each. Completed and failed build elapsed time is clipped to the reporting month, including builds crossing the boundary. Empty successful inventories verify zero only in these named regions. In-progress/malformed/paginated responses remain unknown. Non-eligible machine types or private pools disable the allowance comparison. Other regions/account projects are explicitly outside coverage; elapsed time is not billed rounded minutes. Irregular builds are not projected.
- **Worker safeguard:** the same worker read also supplies its padded runtime reservation against the existing 70-minute budget, in details. This is not total Google trigger runtime; the main metric stays unknown. Runtime and URL Fetch remaining quota are not exposed by Google. No alert code, trigger or deployment changes are needed.

Read-only investigation also queried seven days of the three sparse Monitoring metrics. The main-project delete metric has historical samples but none in the current reporting day; collector-project deletes and main-project log ingestion have no samples in the wider window. All three requests succeeded, so missing read permission is not the cause. Absence cannot distinguish no activity from delayed/unemitted samples and remains unknown; no synthetic zero is used. The source adapter separately classifies missing permission, API/setup gaps, absent samples, incomplete responses, transport errors and quotas Google does not expose. It never enables an API.

References: [MailApp remaining quota](https://developers.google.com/apps-script/reference/mail/mail-app#getRemainingDailyQuota()), [regional build history](https://docs.cloud.google.com/build/docs/api/reference/rest/v1/projects.locations.builds/list), [default build machine](https://docs.cloud.google.com/build/docs/build-config-file-schema), [Cloud Build pricing](https://cloud.google.com/build/pricing).

## Compact dashboard behavior

Cards use **Within allowance**, **Getting close** (80% through 100%), **Over allowance** (greater than 100%), or **Unknown**. Exact exhaustion is described as getting close, never incorrectly greater than the allowance. Current measured use and projected period-end use are separate; projected risk can place a currently healthy card in Needs attention. Stale reports lose healthy statuses, and missing values have no progress bar. Capacity and rolling quotas have no rate projection. Daily/monthly reset dates are shown in the viewer's timezone; capacity has no counter reset and MailApp's exact reset remains unknown.

Attention comes first, followed by compact measured-resource cards. A single expandable notice groups missing measurements by cause. Projects, metric names, measurement timestamps, allowance qualifications and application reservations are under Details. The fixed operating deadline stays visible. Actual spending has one short explanation and optional setup details.

Container-image overage includes an explicitly estimated storage-only cost: `max(0, bytes / 2^30 - 0.5) × $0.000136986/GiB-hour × 730 hours`. For 0.75 GiB capacity this is about $0.025/month, assuming unchanged capacity and the full shared allowance available. It is neither month-to-date spending nor an invoice and excludes transfer, scans and other account projects. [Artifact Registry pricing](https://cloud.google.com/artifact-registry/pricing).

## Actual spending: missing setup

Read-only discovery on October 2, 2026 found no visible BigQuery datasets in either project or the currently linked billing-account projects. The deployment account could list datasets; no actual cost table/data permission was discovered. `bazaarsignal` had billing disabled; `bazaarsignal-510305` was linked to the existing billing account. Neither observation proves historical zero charges. Existing Billing console observations with no rows are not cost records. Cloud Billing account/project APIs describe accounts, links and pricing; operational Monitoring counters are not actual cost records.

The single actual-spending card therefore shows **Unknown**; available-history coverage is also unknown in its details. No complete lifetime total is claimed. No invoice is required. No billing export, billing enablement or paid dependency was introduced.

For actual reported totals, supply an existing standard or detailed Cloud Billing BigQuery export's project, dataset, table and location and grant the reporting backend read access to that table plus bounded query permission. If no export exists, a billing-account administrator must separately choose/configure one; this is not silently enabled by the dashboard. Add a server-side adapter with a dry-run/bytes limit and the existing 30-minute cache before connecting it. Do not query both standard and detailed exports together, which would double-count costs.

The adapter must filter the two project IDs, keep currencies separate, sum cost plus each row's signed credits, and include adjustments exactly once. Show gross cost, credits and adjustments separately. Report the minimum/maximum **usage timestamps actually covered**, export freshness and the current-month usage-time selection; invoice month is a different grouping and can contain late adjustments. Project-unallocated account adjustments/taxes must be explicitly excluded or separately shown, never silently attributed. Empty current-month rows mean **Not yet reported**, not zero. Export history/backfill depends on when and where export was enabled; available-history totals must not be called lifetime totals. Current-month reported costs can change before invoicing.

Sources: [Billing export and availability](https://docs.cloud.google.com/billing/docs/how-to/export-data-bigquery), [standard export schema, credits and adjustments](https://docs.cloud.google.com/billing/docs/how-to/export-data-bigquery-tables/standard-usage), [Cloud Run pricing](https://cloud.google.com/run/pricing), [Google free allowances](https://docs.cloud.google.com/free/docs/free-cloud-features#free-tier-usage-limits), [Hosting quota behavior](https://firebase.google.com/docs/hosting/usage-quotas-pricing), [Apps Script quotas](https://developers.google.com/apps-script/guides/services/quotas).

## Deployment and operational limits

The release changes Hosting and only the existing `marketapi` service. The collector revision, schedule, cleanup and Apps Script alert deployment remain in place. Local images use the existing packaging/smoke-check tooling and consume no Cloud Build minutes. Read-only source inspection scripts and the narrow IAM utility are checked in; local receipts contain no printed access tokens.

Earlier releases used the Monitoring repository gauge and disclosed an apparent existing overage. That conclusion was incorrect: use repository `sizeBytes` for the storage allowance comparison, as documented above. The correction release does not use the existing-overage exception; its measured capacity, conservative image hold and safety margin must satisfy the original 75% free-allowance deployment guard. All compute/log/runtime limits remain in place.

Automatic collector shutdown may remove public Cloud Run invocation. Because reporting reuses that existing service, it then becomes unavailable too; the website shows a reporting-service warning. No privileged bypass or resume control was introduced to defeat shutdown. After the fixed deadline, an operator must review the existing state through authorized Google tooling.

Tests cover verified-owner identity, wrong provider/project/email, expired/revoked/forged token failures, direct HTTP access, auth on cached responses, response privacy, missing/partial/zero measurements, allowance math, DST, concurrency, failure throttling across restarts, ledger preservation, and desktop/mobile identity transitions with no market requests. Browser tests use the local Auth emulator and explicit mocked measurement responses, never production test users or email sends.
