### F1 — Daily archive failure is not recovered or exposed accurately

**Evidence.** The October 29 04:59 Scheduler request returned HTTP 500 after 9.764 seconds. Its logs contain `History storage HTTP 429: RESOURCE_EXHAUSTED` and `daily_history_failed`. A separate ledger retry reported `firestore-write-bandwidth`; this establishes contemporaneous pressure, but does not prove which history shard or index caused the history failure. The 05:00 regular collector succeeded. The archive metadata still reports the October 28 04:59:02.798 successful capture (the October 27 fixed-EST close). The October 28 closing capture did not complete. The sampled Booster Cookie history also ends at the prior close; this is not an exhaustive all-item gap inventory.

**Local reproduction.** In `tests/audit-reproductions.test.ts`, seed 32 shard destinations and old metadata; let the first four-document commit succeed and reject the second commit with 429. `capture()` rejects without a bounded retry. One early shard exposes the new point; a later shard has none. `item()` returns the old `lastSuccess` and `lastError: null` for both. These are valid individual points, but users cannot distinguish failed collection from an otherwise healthy archive.

**Locations.** `collector/cloud-price-history.ts`: `request()` line 112, `write()` line 177, `capture()` line 202, `item()` line 287 and unconditional `lastError: null` line 319. Daily admission/reporting is in `collector/paid-budget.ts` around lines 237–252.

**Impact.** A transient storage failure can lose the only scheduled closing capture and leave uneven shard progress with no returned error. Users inspecting an apparently enabled collector receive stale history without the specific failure diagnosis.

**Proposed fix.** Add bounded, classified transport recovery inside the existing reserved daily invocation, honoring deadlines, cancellation, actual write accounting, and preconditions. Distinguish explicit rejection from an unknown commit outcome; re-read/reconcile before replaying a potentially completed write. Persist a bounded collection error/progress status when possible and return it to charts; provide a stale/missing-close indication even if the error-status write itself fails. Decide explicitly whether partially completed captures remain usable or require a publication manifest. Google recommends bounded handling of transient errors for direct REST users; single-document write capacity depends on workload and indexing. [Firestore best practices](https://docs.cloud.google.com/firestore/native/docs/best-practices)

**Regression tests.** Reject each batch in turn with 429/503, simulate timeout after a successful commit, verify no duplicate daily point, correct error metadata, reserved-cost limits, and expiry. Preserve the intentional scheduler no-retry/durable daily-admission restrictions. Do not reset day receipts or manually backfill production as an automatic “fix.” Effort: medium, with accounting review.

### F2 — Item-page cancellation survives the scheduler's recovery fix

**Reproduce.** Open `/#view=item&item=BOOSTER_COOKIE` at 13:05 with its first selected-price request pending. Hide the page, allow cancellation to settle, then return during the same quarter-hour slot. The page says “Market read interrupted” / “Data unavailable”; request count remains one. Advancing to 13:17 causes the second request and restores the book. Reproduced on both browser sizes.

**Cause/location.** `src/companion/bazaar-search-data.ts` lines 74–86 returns the same slot's selection promise; lines 110–113 clear only `selection.retryAt` after abort. The failed selection remains in the map. The October 27 scheduler correctly resumes unfinished work, but the selection layer supplies its aborted result.

**Impact.** Returning to an interrupted item page can remain unavailable for nearly a full polling interval, despite a reachable service. This is a different consumer/cache gap from the portfolio bug fixed October 27.

**Proposed fix/tests.** Evict only the matching visibility-cancelled selection, preserving newer/in-flight shared selections, completed caches, terminal pauses, and stricter server deadlines. Add tests for return before/after abort settlement, multiple subscribers, and hide/unmount/expiry distinctions. Effort: small. Evidence: `tests/audit-2026-10-29/public/recovery.spec.ts`, [mobile screenshot](measurements/app-audit-2026-10-29/item-cancel-mobile.png).

### F3 — Partial successful replies discard usable prior prices

**Reproduce.** Start with ten units valued at 100 each. At the next scheduled check return HTTP 200 with `{bazaar: [], stale: true, error: 'Partial snapshot unavailable'}`. The previous 1,000 value disappears and becomes incomplete. Advancing another 61 seconds produces no retry. The same return shape occurs when a later batch fails after an earlier batch succeeds.

**Locations.** `src/companion/Workspace.tsx` lines 226–241 replaces `bazaar` with the returned list and resolves successfully. `src/companion/portfolio-market.ts` lines 21–40 returns accumulated partial batches plus error/stale flags without throwing.

**Impact.** A brief partial failure removes previously useful information and bypasses the October 27 failure retry path. Existing incomplete-price labels correctly prevent a false complete valuation/chart point; this is loss of retained information and slow recovery, not a silent zero-value accounting assertion.

**Proposed fix/tests.** Reconcile by item ID, retain old quotes with their original timestamps and explicit stale status, and distinguish transient incompleteness from legitimate missing/delisted products. Schedule bounded recovery for transient failures without creating a loop on permanently missing items. Test failed first/middle/last batches, fresh-plus-stale totals, deleted holdings, policy pauses, and recovery to a complete snapshot. Effort: medium. [Reproduction screenshot](measurements/app-audit-2026-10-29/partial-price-mobile.png).

### F4 — Private data has no cross-tab freshness trigger

**Reproduce.** Open the same portfolio in tabs A and B. Change quantity 10 to 20 in A. Advance B by two minutes, dispatch hide/show and focus. B still displays 10 and its old valuation. Navigating B to Settings and back reads 20. Signing out in A correctly clears B; this test did not find cross-user data leakage.

**Locations.** `src/companion/session-reads.ts` lines 2–20 applies a 60-second TTL only when `read()` is called. Holdings are loaded by the effect at `src/companion/Workspace.tsx` around lines 185–207; focus/visibility and another tab's successful mutations do not invalidate/re-read them.

**Impact.** A user working in multiple tabs can make decisions from old quantities or buying power even while public prices keep refreshing. Optimistic concurrency checks help prevent stale writes but do not refresh the displayed state.

**Proposed fix/tests.** Use a user-scoped mutation invalidation signal and a bounded refresh on visibility return when private data is old. Avoid putting private values in shared public caches; discard pending responses from the previous identity. Test holdings, purchases, rename/delete, balance/preferences, simultaneous edits, and account switching. Effort: medium. [Screenshot](measurements/app-audit-2026-10-29/stale-tab-mobile.png).

### F5 — History loading ignores client expiry

**Reproduce.** Start one minute before November 1 07:00 UTC, remain on the landing page, advance 61 seconds, then open a valid item link. The order book displays “Updates paused” and sends zero price requests, but `/api/price-history` still receives one request. The archive cache can repeat this on another cold item or after its five-minute lifetime.

**Locations.** `src/companion/daily-price-history.ts` lines 29–45 fetches without the paid-mode pause/expiry directive; `src/companion/BazaarPriceChart.tsx` around line 83 starts the load on item mount.

**Impact.** Unnecessary requests and a generic archive error after the known end of service. This does **not** bypass backend expiry, authorize collection, or establish a successful post-expiry admission.

**Proposed fix/tests.** Gate only network history loads on the applicable server/client terminal policy while keeping already cached history readable. Differentiate public archive browsing policy from live-price refresh if retained history should remain available after the pilot. Test cold/warm item navigation at exact expiry, explicit pause, recovery deadlines, and teardown. Effort: small, with a product decision about post-pilot archive availability.

### R1 — Vulnerable dependency version requires a targeted update review

`npm audit --omit=dev --json` in `market-functions` reports six affected dependency entries: one high and five moderate. The lockfile includes `body-parser` 2.3.0. The upstream advisory describes a compressed-request trailing-byte denial of service; patched releases are 2.4.0 and 1.20.9 for their respective branches. [Maintainer advisory GHSA-27r3-jxmh-p828](https://github.com/expressjs/body-parser/security/advisories/GHSA-27r3-jxmh-p828)

The separate root/tooling audit reports 26 affected entries, 18 high and eight moderate. These are dependency entries, not 26 independent reachable production exploits. Vite/emulator/CLI dependencies should not be confused with browser-shipped code. Other server findings include `fast-uri`, `qs`, and the `cloudevents`/`uuid` chain.

**Verification limit.** An isolated localhost child-process probe against installed body-parser 2.3.0 sent gzip plus trailing bytes. It returned HTTP 400 and exited normally; **the probe did not reproduce the advisory crash**. The running production image was not attacked or unpacked. Its lockfile/build correspondence supports a dependency exposure concern, not proof of remote exploitability.

**Proposal.** Review a compatible parser/framework dependency update in a separate implementation task, inspect the resolved production tree, and exercise the exact framework request parser with compressed malformed-body fixtures in an isolated process. Retain limits and authentication checks; a handler guard may run after framework parsing. Do not run `npm audit fix --force` or downgrade the framework based on a transitive suggestion. Effort: small to medium. Evidence: [server audit](measurements/app-audit-2026-10-29/npm-audit-market.json), [root audit](measurements/app-audit-2026-10-29/npm-audit.json), [probe](measurements/app-audit-2026-10-29/body-parser-probe.json).

### R2 — Invalidated emulator session does not clear private UI

**Reproduce locally only.** Sign in through the Auth emulator, create a holding, delete that synthetic Auth account through the emulator endpoint, then force `getIdToken(true)`. It rejects with `auth/invalid-refresh-token`. The Sign out control and private workspace remain. Two desired-behavior assertions fail, one per viewport, in `tests/audit-2026-10-29/private/journeys.spec.ts` line 113 onward.

**Uncertainty.** Firebase SDK handling differs by error code; its automatic invalidation path handles `user-disabled` / `user-token-expired`. Production revocation may return a different code than this emulator deletion. The app's observer in `src/data.ts` lines 47–49 does not add a general terminal-refresh-error transition. No production session was revoked/deleted, and no unauthorized read/write was demonstrated.

**Proposal.** Add a central, identity-aware terminal-session recovery state for confirmed invalid credentials; do not log users out on ordinary offline/network failures. Clear private caches and offer sign-in again. Verify both emulator behavior and provider-documented error semantics in an authorized staging account before declaring production impact. Test expired, revoked, disabled, deleted, offline, and switched sessions. Effort: medium. [Failing assertions](measurements/app-audit-2026-10-29/session-duplicate-rerun.log).

### R3 — Snapshot capacity is close to its hard bound

The 17:50 read measured an encoded Bazaar value of **881,146 B against 917,504 B**, leaving **36,358 B (3.96%)**. A nearby decoded snapshot contained 2,201 items and 7,843,180 B. `collector/inline-snapshot.ts` lines 9–31 deliberately rejects oversized encoded data. Snapshot/transport failures interact with fail-closed runtime handling and can cause a broader pause; exact behavior depends on the failure classification.

This is a fresh headroom measurement of a previously documented size risk, **not another reproduced ledger-reader outage**. The old ledger response bound was 131,072 B; today's 132,414 B ledger response is accepted by the v2 reader's larger reviewed limit. The retained 1,188 inline receipts have not started growing again.

**Proposal.** Track public snapshot encoded size/headroom in existing bounded operational reporting. Before any capacity change, simulate the real 896 KiB boundary and incompressible/larger books. Prefer a reviewed lossless representation/storage fallback that retains all book levels and validates integrity. Do not simply raise the Firestore field limit, drop levels, prune legacy receipts, or weaken accounting. Effort: small for visibility, medium/large for storage redesign.

### R4 — Public invalid traffic spends the finite admission allowance

One mocked `GET /not-a-market-route` through the paid runtime returns 404 but consumes **one admission, four Firestore reads, and four writes**, with zero upstream work. It increments internal reservations by approximately **$0.000603045**; that is not a billed charge. See `collector/paid-budget.ts` lines 255–279 and `tests/audit-reproductions.test.ts`.

The known retired routes and malformed history requests already have early rejection paths; this finding concerns other unknown paths entering the paid handler. Public price access is intentional. Browser CORS is not an abuse-prevention boundary. Repeated low-value requests could exhaust the 4,000-admission limit even when real spending is tiny; no production abuse or load test was attempted.

**Proposal.** Validate the exact public route/method/schema before expensive durable admission, and review bounded abuse protection for valid misses. Preserve accounting for actual work, public access, expiry, and safe shutdown. Consider the cost/complexity of rate limiting before adding infrastructure. Test unknown paths, OPTIONS, invalid assets, valid repeated requests, and exhaustion without allowing unaudited collection. Effort: small for route ordering, medium for any broader admission redesign. [Measured counts](measurements/app-audit-2026-10-29/invalid-route-cost.json).

### Request paths and observed work

1. **Landing/search:** bundled catalog filtering; typing and invalid IDs generate no market requests. A valid selection checks public memory/CacheStorage and Web Lock coordination, then requests up to 100 assets. The public route carries no private portfolio data.
2. **Price API:** each miss takes a durable paid admission, reads control/published data with in-instance snapshot reuse, returns selected prices with gzip when accepted, and finishes durable accounting. It does not fetch upstream market data to satisfy a browser read.
3. **Private workspace:** Firebase authentication and owner-scoped Firestore reads/transactions; `SessionReads` retains a mounted user's reads. Public market caches contain public data; private mutations invalidate that workspace's private entries. F4 concerns missing cross-tab invalidation.
4. **History:** per-item five-minute browser cache; backend reads metadata plus the item's shard for each recorded year, decodes shared public documents, then returns only that item. Response is `private, max-age=300` with gzip and `Vary: Accept-Encoding`.
5. **Collection:** fixed quarter-hour job performs bounded upstream work and writes shared snapshots. The observed 05:00 run made two upstream calls (catalog and Bazaar), 14 observed Firestore reads and nine writes, and reported 2,956 ms handler work; platform latency was 6.816 seconds. This is one natural run, not an average across all slots.
6. **Notifications:** local instrumented existing test reverified six document reads and one ledger commit for three holdings sharing one portfolio when no send/pruning is needed. Shared prices are reused per evaluation pass. Pre-send identity, preference, ownership, revision, and durable delivery checks remain necessary. Actual email delivery is excluded; the last verified worker state is paused.
7. **Admin:** daily published report; opening/reopening does not collect or refresh providers. The existing mocked test makes 100 page reads with two document reads, zero commits/provider calls. The failed-source daily fixture performs five provider attempts and two commits once per day, with no same-day repeat. These are fixture counts, not a production invoice.
