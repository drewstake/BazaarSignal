# Portfolio pivot: behavior and release contract

This document describes the portfolio implementation dated October 4, 2026. It supersedes the product behavior in historical discovery/market documents. The user authorized commit, push and deployment of the paused portfolio release; see [release evidence](PORTFOLIO-RELEASE.md). Collection, billing changes, new services, production data deletion and real test emails are outside this release.

## Bazaar-only removal — October 4, 2026

Auction pagination, NBT decoding, listing normalization, fee calculations, exact-ask valuation, the selector catalog and entry forms have been removed. The collector permits only catalog, election and Bazaar jobs, even with old saved auction demand. Retired auction routes return 410. New auction snapshot writes are refused before storage I/O. Legacy policy fields, history, held usage and stored blobs are preserved; no counters are reset or refunded. Existing unsupported records cannot trigger price reads or visible demand.

Collection was already disabled, so this source change does not claim a reduction in current production API traffic. The smaller builds reduce future transfer/artifact storage after deployment. Retained production snapshots, old Hosting versions and container artifacts still consume storage; they have not been purged. Collection, notifications, email and scheduled jobs remain paused. This removal does not enable a paid plan or a 30-second cadence.

Validation: 392 unit tests, 29 Firestore-emulator tests, and 26 desktop/mobile browser tests passed; UI/Apps Script, market-functions and collector builds passed. Compiled collector bundles contain no auction upstream endpoint. The emulator requires the existing Java 21 runtime in .local/java21 on PATH. Rollback uses the prior Git revision and deployment artifacts; stored records and accounting remain compatible. Deploy only with the existing allowance/deployment guard satisfied, keep the release paused, verify retired routes and Bazaar cached reads, and separately re-evaluate cadence before activation.

## Product and valuation

The portfolio screens retain the original BazaarSignal visual design: sky-island scenery, hanging wooden branding and navigation, parchment panels, Tektur/Barlow typography and illustrated item icons. Reusable styling is preserved in `src/companion/skyblock-theme.css`; the navigation and content reflect the portfolio product.

Portfolios, Notifications, Account, and owner-only Usage & Costs replace discovery and watchlists. Holdings are manually recorded, not synced from inventory. The same asset may appear in multiple portfolios. Within one portfolio the stable Bazaar ID has exactly one holding document. Edits preserve asset identity; additional purchases use the Positions parser and weighted-cost utility inside Firestore transactions. Stale replacement edits and deletes fail instead of overwriting newer purchases.

Average purchase price and total cost basis are alternate authoritative inputs; switching converts the entered amount. Quantities are actual whole counts, never inferred. Only Bazaar items can be added. Previously saved unsupported assets remain readable and deletable, with unavailable prices; they cannot be edited, purchased, valued or monitored.

Bazaar uses the highest normalized `bids` / upstream `sell_summary` price, never asks or quick-status averages. Indicative value is quantity × reference, before fees and slippage. Full-quantity liquidation walks all available bids and requires compatible fee evidence; insufficient depth never extrapolates. Future and malformed samples are excluded.

Stale prices display as last-known estimates. Missing evidence displays unavailable. Totals show all acquisition cost but compute P&L only from available values and their matching cost bases, with incomplete coverage explicitly stated. Aggregate percent is aggregate P&L / matched basis, never an average of individual percentages. No history, charts, past returns, executable Auction House proceeds or inventory quantities are fabricated.

## Private persistence and migration

Verified Google accounts own only their own `users/<uid>/portfolios/<id>` and nested `holdings/<assetId>` documents. Rules reject extra fields, fractional/out-of-range quantities, invalid costs, changed asset identities and incorrect revisions. Legacy asset configuration validation remains only to preserve saved records and allow their deletion. It cannot produce market evidence or a deliverable notification.

Notification settings are in `users/<uid>/portfolioNotifications/<portfolioId>__<holdingId>`. Clients cannot create or edit trusted settings/baselines. The verified backend validates owner, parent, holding, thresholds, source and revision and commits with Firestore preconditions. The one permitted client settings mutation atomically retires a notification when its holding is deleted. Preferences store only a boolean at `users/<uid>/portfolioPreferences/main`; recipients cannot be supplied by clients. Server-only `portfolioDelivery/<uid>` holds crossing state/outbox, and `portfolioSubscribers/<uid>` is the worker index. These, private holdings, costs, quantities, membership and settings never enter public cache responses.

On first load per authenticated session, each valid `users/<uid>/positions/<itemId>` is copied unchanged in quantity, cost and acquisition timestamps into portfolio `default` (display name **My portfolio**). The holding and `positionMigrations/<itemId>` marker commit together. The original remains preserved and becomes read-only once marked. Concurrent migration losers accept only a durable winner marker. Invalid sources stop safely with an error. An unexpected pre-existing destination is not merged or overwritten. Fixing a bad source allows the next load to retry; completed markers prevent duplicates. A deleted default portfolio stays deleted. No account gets a default portfolio unless it actually has saved Positions, and no account gets sample holdings.

Portfolio/holding deletion uses private tombstones. Portfolio tombstones cannot be resurrected; holding identity may be explicitly re-added but its old notification remains retired. These tombstones preserve retry safety and make parent/holding deletion visible to delivery checks. They are not a data-erasure claim. Hard deletion/export policies and any production purge require a separate release. Account changes remount the private workspace; stores capture the actual Firebase User object and reject late reads/writes after session replacement, including leaving and returning to the same UID.

## Notification semantics

A notification belongs to one holding. Upward thresholds are at least 0.01%; downward thresholds are 0.01–99.99%. Either or both can be configured. These are changes in the selected per-unit reference, not after-fee liquidation returns.

- **Average acquisition:** basis / quantity. Additional purchases and edits change the baseline and prime the next fresh observation, without sending from that edit.
- **Captured sample:** server-captured, eligible reference and timestamp at save-and-enable. Purchases/edits retain it. Resume requires a fresh same-source observation but retains the original captured baseline. Editing and saving explicitly recaptures it.
- First valid observation establishes the starting side and sends nothing, even if already outside a threshold. A later fresh sample crossing inclusively to or beyond a threshold queues one event. Staying outside does not repeat it. A fresh return strictly inside that threshold rearms that direction. Up/down sides rearm independently.
- Replayed/older source timestamps do not re-evaluate. Stable event IDs include notification revision and monotonically increasing crossing sequence. Crossing transition and outbox persist atomically with parent/holding preconditions before delivery.
- Pause, edit and delete cancel unsent work. Resume/edit prime the next observation. Missing/stale/fixture data never triggers and requires priming the next eligible sample. Source changes suspend evaluation until explicit edit-and-enable; captured baselines are never silently interpreted using another source.
- Deleted holding/portfolio, disabled email preference, unverified/disabled identity and exhausted quota prevent delivery. The worker rechecks parents, configuration revision, relevant holding revision, preference and verified Google account immediately before sending. An already in-flight email cannot be recalled. A brief pause/resume of preferences between worker ticks cannot be observed, but disabled preferences are rechecked at delivery time.

The new outbox reuses the existing delivery engine: shared MailApp quota check before each send, persisted claim, ten-minute lease, independent user-scoped receipt, one-hour quota deferral, 1/5/15/60-minute failure backoff, five-attempt bound, and 45-second worker budget shared with the legacy job. There is no paid fallback. Acceptance is not inbox receipt; a process crash between MailApp acceptance and receipt persistence can still duplicate an ambiguous send. Terminal records expire after 30 days while crossing sequences retain deduplication; 250 retained/pending events per account stop new queueing until room is available, bounding the combined workflow/outbox document.

New settings share legacy admission controls: maximum 20 active and 100 stored alerts per account, 5 new/hour, 20 new/day and 40 new/day across the site. Creation itself sends no confirmation or test email. Only email is exposed because the currently deployed Apps Script sender supports it; historical Discord simulation code is not claimed as a deployed delivery channel.

## Legacy records and alerts

Old watchlists and filters are now read-only private archives. Status, backend ledgers, receipts and capability hashes remain preserved. Old standalone create calls refuse new records, but an identical retry for an existing request ID returns its prior status. Legacy account reads, existing target-update primitives and explicit disable capabilities are retained for compatibility. Notifications has a dedicated legacy review/disable section; it does not convert targets or turn on new notifications. Fresh legacy price evaluation is retired; already queued messages retain existing delivery semantics.

The October 4 retirement policy preserves every legacy alert and disable link, stops fresh evaluation, and drains only previously queued or recoverable in-flight mail. The worker retires empty active-work indexes without deleting ledgers. An idle cache prevents repeated reads for an hour, and an unchanged ledger is not rewritten. Existing owner/backend migration logic preserves its original rollback document. Private rollback snapshots and counts are saved under `.local/portfolio-release-before/`; no purge is part of this release.

## Collection and verified cost claims

The supported upstream price endpoint is `/v2/skyblock/bazaar`, which returns a products snapshot. Visible Bazaar holdings share one collection and cache; additional users and tabs do not create additional upstream collectors.

Server-only demand scanning uses bounded pages, deduplicated parent reads, pre-I/O allowance reservation, complete-report requirements and a 10,000-row scan ceiling. Deleted parents/holdings are excluded. Asset keys are deduplicated across accounts; the demand report contains no UID, portfolio, quantity, basis or notification preferences. No raw private scan is exposed publicly. Eligible notifications are a subset of these holdings. A future enabled scheduled adapter feeds only required market jobs into the existing shared CAS collector inside existing allowance admission; failed/incomplete/stale demand fails closed. No user or holding creates an upstream poller.

A nonempty Bazaar demand needs one shared Bazaar snapshot plus due item-name and fee metadata. Legacy auction-only demand produces no collection jobs. Public responses contain only requested Bazaar assets. Browser requests reuse in-flight deduplication, Web Locks, bounded CacheStorage, timestamps and pause/backoff controls. The backend processes at most five subscribed accounts per batch with a shared snapshot request for at most 100 active Bazaar asset keys. Account fairness uses a durable cursor.

Verified locally: 200 private rows for the same Bazaar asset collapse to one public asset key; demanded market jobs appear once; disabled collection/evaluation performs no collector/worker I/O; no market calls occur during paused browser journeys; allowance exhaustion prevents the demand read. These are unit/emulator/browser measurements, **not production request or billing savings**. No live request-count reduction or cost saving is claimed. Existing measurements of broad auction page counts in ZERO-COST-AUDIT remain historical evidence, not a new benchmark.

## Local workspace

`npm run dev` and `npm run dev:local` launch Vite on loopback port 5173 and Firestore on loopback port 8080. Existing Google sign-in verifies the actual account; portfolio data uses a separate local database with this repository's rules. The development-only notification adapter verifies tokens with Firebase Auth, then runs the same ownership/schema/admission validator and atomic Firestore preconditions as the Apps Script implementation. Acquisition-baseline settings support create, edit, pause, resume and delete. Capturing a new market baseline remains unavailable while evaluation is paused. No evaluator, mail sender or collector starts.

Existing cloud holdings, Positions and legacy alerts are not copied or modified by this local mode. The on-screen notice identifies local records. Data imports from `.local/local-workspace-data` at launch and exports there on orderly shutdown; stop with Ctrl+C to preserve changes. A running instance can be backed up with `npm run backup:local`. The launcher and backup helper recover completed exports when Windows prevents Firebase CLI's final directory rename; recovery retains the source snapshot. Abrupt termination can lose changes since the last export.

Owner Usage & Costs reads `.local/usage-dashboard-measured.json` if present, retains the original measurement timestamps, and explicitly labels the report historical and out of date. Refresh reloads that file; it does not contact the cloud collector or imply current allowance headroom. If absent, live usage is unknown. All local API routes require verified identity, and the report additionally requires existing owner authorization. `npm run dev:ui` is the bare Vite entry point for isolated tests; running it against old production rules does not enable the new portfolio backend.

## Release controls

1. Back up legacy Positions/alerts, review source, tests and screenshots, and deploy rules/indexes, Apps Script and frontend together. The October 4 user authorization covers this release. Keep both portfolio policy constants false and the existing market pause active.
2. Retire fresh legacy evaluation using the queue-drain policy above. Preserve disable links, idempotency and original records. No silent conversion, new opt-in or production purge.
3. Before live pricing/notifications, verify provider-enforced zero-cost capacity and all existing allowance reports. Meter the additional original-project private reads separately, authorize the collector service account's least-privilege access to original-project holdings if needed, and validate the admin Auth lookup used by delivery. The scanner reserves conservatively through the existing meter, but cross-project free allowances and actual read volumes still need release evidence. Collection and notification policy gates plus deployment deadlines must be reviewed together; changing a date alone cannot resume this release.
4. Test the disabled rollout with emulators/offline mail mocks. Real delivery tests, collector restarts, billing changes and paid services need separate authorization. The release guard's `--paused-portfolio` mode updates the two existing service images while verifying the existing hourly schedule stays PAUSED, preserving allowance identity, deadlines, counters and IAM. It cannot resume collection.
