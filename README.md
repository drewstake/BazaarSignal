A private SkyBlock portfolio tracker for manually recorded Bazaar items. Create named portfolios, record acquisition costs and additional purchases, inspect estimated value and unrealized returns, and choose holding-based percentage notifications. Previously saved Auction House records remain preserved.

The interface uses a night-market theme with lantern-lit scenery, mint accents and pixel headings. Portfolio value history records complete observed estimates on the current device, with day/week/month/all views and up to 90 days of retained snapshots. Purchases and holding edits affect the value chart; unavailable prices never create a false drop. Holding rows expose compact edit, notification and delete actions. Editors open in dialogs, notifications preview their target prices, and alerts can be edited directly in Settings. Each portfolio can also record available coins as buying power.

The paid pilot preserves existing authentication and private records, with hourly Bazaar collection and opted-in email checks behind expiration and budget gates. The [earlier portfolio release evidence](docs/PORTFOLIO-RELEASE.md) and [zero-cost audit](docs/ZERO-COST-AUDIT.md) are historical records of the paused deployment.

- Portfolio is the landing page. Stable links use `#view=portfolios&portfolio=<id>`, `#view=settings&section=notifications`, `#view=settings&section=account`, and owner-only `#view=admin`. Legacy notification/account links redirect to their Settings section; `#view=usage` redirects to Admin. Old discovery, watchlist, positions and standalone-alert routes redirect to Portfolio. Existing `#disable=<capability>` links still require explicit confirmation.
- Holdings remain editable without prices. Quantity is always a whole number; coin inputs accept commas and case-insensitive k/m/b. Auction quantities count identical stacks, with acquisition price per stack. Asset configuration is immutable; record materially different variants separately.
- Legacy Positions copy to **My portfolio** using an atomic per-item migration marker. Originals remain intact. Retries do not duplicate holdings, and deletion does not resurrect imports.
- Bazaar unit prices, portfolio values and new holding alerts use the lowest sell offer (best ask), before selling fees. Immediate after-tax liquidation estimates still use complete buy-bid depth and compatible fee evidence. Sell offers are indicative, not guaranteed proceeds. Previously saved bid alerts retain their original basis until edited.
- Holding notifications support upward/downward percentage crossings against average acquisition price or a fresh server-captured sample. Configuration sends no mail. The paid pilot evaluates opted-in notifications hourly; unavailable or stale source prices cannot trigger an alert. Email preferences default off.

## Local development and verification

Use Node.js 24 and `npm ci`. Configure the existing BazaarSignal public Firebase client values in `.env.local`. `npm run dev` (or `npm run dev:local`) starts the app at **http://127.0.0.1:5173** with real Google sign-in and a separate local Firestore database. Java 21 is required; the launcher also finds the existing JRE under `.local/java21/`. Portfolios, holdings and notification settings are editable locally without deploying cloud rules. The launcher imports saved data from `.local/local-workspace-data` and exports it on orderly shutdown; stop with Ctrl+C to preserve changes. No collector, notification evaluator or email sender starts.

The owner-only Admin page serves a saved daily snapshot. The existing server clock collects supported measurements once per UTC day around **12:10 UTC**; opening the page never triggers collection and there is no Refresh button. A durable daily attempt slot prevents duplicate scans and retains failures until the next day. Private server and in-memory client caches reduce repeated report reads. Unsupported sources retain their original measurement times. Local Admin only reads the published report and cannot collect measurements or mutate production records. Actual Google charges remain unavailable without a readable billing export; reservations are separate estimates. See [Admin sources and schedule](docs/ADMIN-RELEASE.md). `npm run dev:ui` starts Vite alone for test harnesses or a separately configured backend; it does not supply local persistence. `?fixtures=1` is development-only, clearly labeled, and cannot trigger notifications.

- `npm run dev:preview`: public UI preview at http://127.0.0.1:5173 using the live website's cached prices. Typing and opening search make no market requests. An uncached selection makes one selected-item GET through a development proxy; the existing browser cache reuses it across selections, tabs and reloads for the hourly window (subject to cache limits). Portfolio views reuse their existing batched price route. No full market download, presence request, local collector or upstream refresh is started. Each uncached GET uses the existing Google budget; proxying avoids CORS preflight requests. The same fixed release, expiration and server safeguards apply. Samples retain their original timestamps and can still be stale. This mode deliberately disables Google sign-in; stop it and use `npm run dev:local` to sign in and save local portfolios.
- `npm run dev:preview:offline`: use only the saved local SQLite snapshot with zero cloud market reads. `npm run dev -- --offline` does the same for the signed-in local workspace. Ordinary `npm run dev` now uses the shared cached-price API while keeping private portfolio storage local. Offline and shared market caches have separate URL namespaces.

Selecting a header search result opens a public item page at `#view=item&item=BOOSTER_COOKIE` (or the selected catalog ID). **Copy item link** creates a direct link on the current host without private portfolio or query parameters; local links require the local server, while deployed links use the website's public host. Direct visits, reloads, and browser Back/Forward work without signing in. Unknown or excluded IDs make no market requests.

Item pages show saved sell offers and buy orders together, with every returned price level visible (up to 30 per side). Compact tables sit side by side on desktop and mobile, with no toggles or expansion controls. Background volume bars show each level's item quantity relative to the largest level across both sides; they are not traded-volume history or cumulative depth. Prices, depth, and bars are calculated locally from that book. Typing, copying links, and reading the entire returned book make no market requests. Pages reuse downloaded portfolio/market data and the existing hourly browser cache across navigation, reloads, and tabs; an uncached valid item uses the same single selected-item GET as the former panel, subject to existing cache limits and safeguards. No full-market order books, private portfolio reads on direct item visits, or upstream refreshes are added.

While an item page is visible, the existing scheduler checks its selected item once per hourly read window, at two minutes past the hour to allow publication. A stricter server interval or budget backoff delays the check. Hidden pages stop scheduling and abort their pending read; returning performs at most one due check without replaying missed hours. Leaving the item page stops its scheduler. A new snapshot already downloaded by a portfolio or another tab is reused; otherwise a check can make one selected-item cached-data GET. Failed or interrupted attempts are retained for that window rather than retried repeatedly. Pauses and expiration stop further checks. Collection schedules, Google budget limits, release expiration, and usage safeguards are unchanged.

A valid sample is labeled **Hourly snapshot** until it reaches one hour plus the existing two-minute publication/read allowance; older samples, invalid timestamps, explicit stale flags, and failed reads remain labeled stale. The sample time, timezone, and age stay visible; the timestamp retains its full date on hover and in the semantic time element. Depth totals sit under each price, and secondary snapshot and volume-bar explanations are available under **About this data**. This display rule does not change the stricter three-minute freshness checks for trading or alerts, collection, cache reuse, budget limits, or expiration.
- `npm test`: valuation, percentage notifications, private backend boundaries, quotas, caches, allowances and shared collection tests.
- `npm run test:local`: notification mutations against an already-running local workspace, using disposable records and the actual backend validator. Leaves existing local portfolios intact.
- `npm run backup:local`: back up the running local database; recovers completed exports after Windows directory-rename failures.
- `npm run test:rules`: Firestore emulator ownership/schema, migration and concurrent-transaction tests. Requires Java 21; the existing local JRE is under `.local/java21/`.
- `npm run test:browser`: isolated Auth/Firestore emulator desktop and mobile journeys, including owner Admin, Settings, and legacy links. Never sends mail or contacts a market service.
- `npm run build`: production frontend and Apps Script bundle/type checks.
- `npm run build:collector` and `npm run build:market-functions`: local-only infrastructure builds.
- `node scripts/profile-app.mjs current` and `node scripts/profile-chart.mjs current`: repeatable offline browser/cache and chart profiles under `.local/audit/`; no cloud requests or mail. The audit documents their measurement limits and the lossless artwork exporter.

The test harnesses use separate Auth/Firestore ports 9098/8081 and can run while the local workspace stays open on 5173/8080. Run the two test harnesses sequentially because they share their test ports.

The legacy discovery UI, watchlist, opportunity inspectors, filter/ranking controls, standalone alert forms and public UI-kit gallery have been removed. Shared market normalization, comparison, fees, caching, authentication and legacy delivery primitives remain where needed for portfolio valuation or safe record retirement. No package dependency became wholly unused: Firebase and React serve the app; hashes, compression and Redis still serve shared infrastructure.
